# H.264 live video path (`screenrecord` → WebSocket → WebCodecs)

**Date:** Sun Sep 20, 2026 · **Status:** shipped, default-on (`H264_ENABLED=1`)

The JPEG `FrameBroker` is still here and still correct — it is now the
*fallback*, not the main path.

## Why `screenrecord`, not scrcpy

| | `adb exec-out screenrecord --output-format=h264 -` | scrcpy / ws-scrcpy |
|---|---|---|
| Deploy | nothing to install; ships in every Android image (v1.3 here, API 34) | push `scrcpy-server.jar`, keep it version-matched to the device |
| Protocol | one Annex-B byte stream we already know how to read | own control/video protocol + Java server lifecycle |
| Failure mode | process exits, we respawn | jar/ABI mismatch, device-side crash, extra port |
| Cost | Annex-B has no length prefixes, and the encoder rarely emits IDRs | length-prefixed frames, IDR on request |

The two costs are real; both are handled in `app/h264_stream.py` (see below).
Given one emulator and a demo that must not break at a pitch, "nothing to
install on the device" was worth more than "cleaner framing".

## Pipeline

```
screenrecord (device, AVC baseline 540x1200 @1.5Mbps)
  → adb exec-out stdout (SSH tunnel)
    → H264Broker: Annex-B → access units → GOP buffer + fan-out
      → /ws/h264 (one binary message per AU, 16-byte header)
        → browser VideoDecoder (WebCodecs) → <canvas>
```

Transport ladder in `static/index.html`:
**H.264/WebCodecs → JPEG WebSocket → MJPEG → polled `/adb/preview`.**
The JPEG socket stays connected until the first decoded H.264 frame paints, so
a browser without WebCodecs — or a device where `screenrecord` fails — never
shows a blank phone. The upgrade is invisible except for the badge flipping to
**Live · H.264**.

## The three problems `screenrecord` hands you

### 1. No length prefixes → the last frame never flushes

Annex-B only proves a NAL ended when the *next* start code arrives. On a static
screen there is no next frame, so the final frame — the one the user is looking
at — would hang in the parser forever.

Fix: publish a buffered NAL after the pipe goes quiet, but only after **two
consecutive quiet ticks with an unchanged buffer**, where the tick is
calibrated from the largest mid-NAL stall actually measured on this link
(`intra_gap_max_ms`, capped at 120 ms). A stalled TCP write mid-NAL looks
exactly like a finished frame for one tick; it rarely survives two.

If we still publish early, `_split_nals` sees the orphaned tail as non-NAL
leading bytes and reports it. That is a **mis-flush**: the window widens 1.6x,
a fresh IDR is requested (nothing else repairs a corrupt reference frame), and
the window decays back once 120 clean AUs pass. Measured on this box: tick
settles at 30–65 ms, `misflushes: 0` across all QA runs.

### 2. IDRs are rare → late joiners have nothing to decode

This build emits one IDR at start and then essentially none. A joiner who just
starts listening gets P-frames referencing frames it never saw.

Fix: a bounded **GOP buffer** (AUs since the last key AU, ≤3 MB / ≤600 AUs).
A joiner replays it and has a picture instantly (the browser fast-forwards
through it in one burst — that is the 100–200 fps blip in the HUD on connect).
If the GOP is too big to replay cheaply (>1 MB) *and* the joiner is alone, we
restart the encoder for a fresh IDR instead. Restarting when others are
watching would freeze them for ~700 ms, so we don't.

### 3. Recording is time-limited

`--time-limit 0` removes it, but we re-segment every 60 s (`H264_SEGMENT_S`)
anyway: each segment starts with SPS/PPS + IDR, which is what keeps the GOP
buffer small and joins cheap.

## Wire format (`/ws/h264`)

One binary message per access unit — no JSON/binary pairing to correlate:

```
offset 0  u8   version (1)
offset 1  u8   flags — bit0 = key frame
offset 2  u16  reserved
offset 4  u32  sequence
offset 8  f64  timestamp (µs, decoder PTS)
offset 16 …    Annex-B payload (SPS+PPS prepended on key AUs)
```

Text messages are control/telemetry: `hello` (codec string parsed from the live
SPS, encoder size, device size, GOP readiness), `ping` (heartbeat), `stall`
(the screen is simply static), `bye` (disabled or at capacity).
Client → server: `pong`, `keyframe`, `ping`, `stats`.

## Concurrency and backpressure

* **One producer.** One `screenrecord` for all viewers; `H264_MAX_CLIENTS`
  (12) viewers, the 13th is accepted then closed **1013** with a reason, so the
  browser falls back instead of retrying a blind 1006.
* **Per-client queues.** 180 AUs / 4 MB. Overflow drops the AU; dropping a
  P-frame sets `needs_key` (no garbage on the wire), a key AU drains the
  backlog instead. Verified 12 viewers, identical AU sequences, **0 drops**.
* **Heartbeat GC.** Both sockets ping every `WS_PING_INTERVAL_S` (15 s) and
  drop a viewer that has not ponged within `WS_PING_TIMEOUT_S` (40 s) — this is
  the fix for the ghost tabs that used to inflate `subscribers`. Verified: a
  client that ignores pings loses its slot and the slot is reclaimed.
* **Idle stop.** No viewers for 10 s → the encoder is released; the device is
  idle when nobody is watching.
* **Input is never behind the video.** `adb shell input …` stays concurrent;
  taps measured 71–172 ms with 12 viewers streaming.
* **Coexistence.** `screencap` still works while `screenrecord` runs, so
  `/adb/preview`, `/adb/screenshot` and the pilot/chat agent are unaffected
  (measured 515 ms / 945 ms during a live stream).

## Ops

```
GET  /adb/h264/stats     producer, viewers, fps/kbps, GOP, misflushes, flush tick
POST /adb/h264/keyframe  force a fresh IDR (restarts the encoder, rate-limited 2.5s)
GET  /health             includes the whole h264 block
```

Env knobs: `H264_ENABLED`, `H264_WIDTH` (540), `H264_BITRATE` (1500000),
`H264_MAX_CLIENTS` (12), `H264_SEGMENT_S` (60), `H264_IDLE_STOP_S` (10),
`H264_GOP_MAX_BYTES` (3M), `H264_GOP_MAX_AUS` (600),
`H264_GOP_REPLAY_MAX_BYTES` (1M), `H264_QUEUE_MAX_AUS` (180),
`H264_QUEUE_MAX_BYTES` (4M), `H264_FLUSH_IDLE_MS` (30),
`H264_MAX_INTRA_GAP_MS` (120), `H264_KEYFRAME_COOLDOWN_S` (2.5),
`WS_PING_INTERVAL_S` (15), `WS_PING_TIMEOUT_S` (40).

## Verification

```bash
.venv/bin/python scripts/h264_probe.py 12 --late-join      # broker only, no HTTP
.venv/bin/python scripts/h264_ws_probe.py --clients 3      # /ws/h264 end to end
.venv/bin/python scripts/qa_h264_browser.py                # real Chromium, WebCodecs
.venv/bin/python scripts/qa_h264_browser.py --no-webcodecs # fallback ladder
.venv/bin/python scripts/qa_stream_load.py --n 13          # cap, fan-out, backpressure
.venv/bin/python scripts/qa_latency_ab.py --rounds 3       # H.264 vs JPEG, same actions
ffmpeg -v warning -i /tmp/ws.h264 -f null -                # the captured stream must decode clean
```

`ffmpeg` decoding the captured `/ws/h264` payload with **zero warnings** is the
parser's real test — it catches exactly the truncation that a browser would
merely render as a smear.

## Honest limits

* **The device, not the pipeline, is now the floor.** Measured raw (no app code
  involved): after a discrete keypress the encoder's first bytes appear
  23–589 ms later, depending on when SurfaceFlinger composes. Nothing in the
  host can undercut that.
* **A single keypress with no follow-on animation can still be quicker on
  JPEG**, because that path force-captures (`nudge`) instead of waiting for the
  encoder. H.264 wins decisively on app launches and anything animated, which
  is what the viewer actually spends its time on.
* Rotation is handled by restart (the segment ends, geometry is re-read), which
  costs a ~700 ms freeze.
* No audio (unchanged, deliberate — TTS plays in the laptop browser).
* Still one device / one ADB serial; nothing here makes it multi-tenant.

## Update — scrcpy-server producer (2026-09-21)

Default source is now **`H264_SOURCE=auto`**: try `scrcpy-server` raw Annex-B
(see `SCRCPY.md`), sticky-fallback to `screenrecord`. Wire format `/ws/h264` and
