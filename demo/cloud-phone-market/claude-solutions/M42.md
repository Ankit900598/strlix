## Mistake restated
Competitors render 20+ simultaneous live video thumbnails at 100–160 px wide with no focus/zoom tier. Nothing on the screen is legible (app icons, OTP digits, error toasts), so operators tap the wrong device or the wrong coordinate inside the right device. It survives because "see 1,000 phones at once" is a demo-friendly sales slide, even though real work is always 1–3 phones deep plus a watchlist.

## Strlix solution (concrete UX + IA)
**Three-tier viewport, never a flat grid.**

1. **Stage (always exactly one phone, ≥360 px wide, live 30 fps, interactive).** The only surface that accepts taps. Everything else is read-only by construction — no click handler at all, so mis-taps are impossible, not just discouraged.
2. **Rail (up to 8 pinned phones, 96 px, 1 fps poster frames).** Not video. A screenshot refreshed every 1000 ms plus a **status chip** that carries the information the pixels can't: `▶ running / ⏸ idle / ⚠ ANR / 🔒 OTP / ● offline`. Clicking promotes to Stage; the previous Stage phone demotes to the rail. One phone interactive at a time, always.
3. **Fleet table (everything else, default view above 8 devices).** Rows, not thumbnails: device name, Android level, current foreground package, last AI action, battery/uptime, status chip. Sortable, filterable. Text is legible at any count; 1,000 rows is a scrollbar, not a mosaic.

**Density, honestly served.** The "wall" people buy is a **Signals view**: one 12 px tile per device colored by state only, zero video. It answers "is anything wrong across 400 phones" far better than 400 unreadable videos, at ~0 bandwidth.

**AI inside the phone.** Each device runs its own agent; the Stage shows an in-phone overlay strip (last action, next action, Pause). Rail/table rows surface `needs_human` — the agent raises a flag, the operator promotes that phone to Stage, resolves, returns. The fleet is driven by exceptions, not by staring.

**Guardrails.** Promote is animated 180 ms so the operator sees *which* phone arrived on Stage. Destructive actions (reset, uninstall, wipe) require the device to be on Stage and type-to-confirm its name. Stage phone name is shown at 20 px above the frame.

Reuses existing `:8789` stream endpoint for Stage only; posters are a new cheap JPEG path so the rail costs one decode per second, not 8 video pipelines.

## Android 7+ / graceful degradation notes
- Android 7–8 hosts: no `MediaProjection` H.264 path guaranteed → Stage falls back to MJPEG at 12 fps; rail falls back to 0.2 fps posters.
- If WebRTC fails entirely, Stage degrades to poster + tap-coordinate posting (blind-ish but usable); UI labels it `LOW-FI` in the frame header so nobody assumes live.
- Under 2 Mbit/s or `navigator.connection.saveData`, rail auto-collapses to status chips only; Signals wall becomes the default multi-device view.
- Operator viewport < 700 px wide: rail moves to a horizontal scroller under Stage; table hides all but name/status.

## Acceptance criteria
- At any moment exactly one device accepts input; rail/table/signals frames have no pointer handlers (verifiable by test asserting zero listeners on non-Stage frames).
- Stage renders ≥360 px wide at all supported viewports; text rendered in the guest phone at 14 sp is legible in a screenshot diff test.
- With 400 devices connected, the client holds ≤1 live media stream and ≤8 poster pollers; bandwidth stays flat as device count grows.
- Every non-Stage device communicates state via a text/color chip, never by requiring the operator to read its pixels.
- Destructive actions are blocked unless the target device is on Stage and its name is typed.
