## Mistake restated
Competitors hand a novice a booted, empty Android home screen with zero orientation. No goal, no first action, no proof the stream is "real." The user pays for a session, stares at a wallpaper, asks "what do I do?", and bounces before the first meaningful tap. It persists because tours are design work that power users skip, so they get cut.

## Strlix solution (concrete UX + IA)
**Principle: the tour lives *inside the phone frame*, not in an external chat or modal overlay chrome.**

1. **Intent capture before boot (pre-warm screen).** While the instance provisions (~8-20s), show 4 big cards: *Run a specific APK · Test my app · Farm/multi-account · Just explore*. Selection is stored as `session.intent` and drives the tour script — no generic tour.
2. **First Tap Target.** Once streamed, a single pulsing ring renders as a *stream overlay layer* (canvas coords mapped to device coords, so it tracks resolution/rotation) over one real UI element. Copy above the ring: "Tap here to open Settings → confirm your phone is live." One tap. Success is detected by the tap ACK from the input channel, not by a timer.
3. **3-step ladder, max 25 seconds.** Step 1 = any tap (proves control). Step 2 = intent-specific (install APK: opens the Strlix drag-drop dock; test app: opens ADB pair card; explore: opens Play Store). Step 3 = "Pin this" — teaches session persistence/resume, the #1 churn question.
4. **AI is in-phone.** The assistant is a floating Strlix bubble *inside* the device viewport (a system-overlay-style FAB). Tapping it opens a sheet docked to the phone bottom edge; it can *execute* ("open Play Store for me") via the input channel, then hands control back. No side-panel chatbot.
5. **Escape hatches.** "Skip tour" always visible; skipping sets `tour.skipped=true` permanently per account. Power users lose ~1 click, once.
6. **Resume, don't restart.** Tour progress persists server-side; a dropped stream resumes at the same step.
7. **Stuck detector.** 20s of zero input events → the bubble self-opens with one contextual nudge, then never again that session.

## Android 7+ / graceful degradation notes
- Hotspots are host-side DOM/canvas, so no on-device API dependency — works down to Android 7 images.
- Coordinates from a normalized 0-1 device space → immune to 720p/1080p instance profiles and DPI.
- If tap-ACK telemetry is unavailable (older agent build), `TourEngine` falls back to a 6s timeout advance plus a "Done" button.
- `prefers-reduced-motion` → static ring, no pulse. WebGL absent → hotspots render as absolutely-positioned divs.
- Low bandwidth (<300kbps): tour text renders host-side, unaffected by stream degradation; hotspot stays anchored even on frozen frames.

## Payment notes
Tour runs on a free trial instance, so no charge path. If the user hits step 3 ("Pin this") past trial, show a test-mode Stripe/Razorpay stub checkout (`STRLIX_PAYMENTS=test`, card `4242…`) that returns a mock `sub_test_*` and unlocks pinning locally. No real charges; live keys gated behind a separate env flag.

## Acceptance criteria
- A first-time user reaches a confirmed real tap on the streamed device in **≤ 30s** from session ready, with tap-ACK verified (not timer-assumed).
- Tour steps are selected by captured intent; the four intents produce four measurably different step 2s.
- Skip is one click, persists across sessions, and never reappears.
- Tour resumes at the correct step after a forced stream reconnect.
- Hotspots stay within 2% of target center across 720p/1080p and after a rotation event.
