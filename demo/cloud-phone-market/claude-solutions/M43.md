## Mistake restated
DuoPlus-style "share device" produces a permanent, unauthenticated URL that grants full interactive control of a running Android instance. Anyone who forwards the link inherits the session: logged-in accounts, SMS/OTP inbox, clipboard, files. No expiry, no viewer-vs-controller split, no watermark, no revocation, no audit. Vendors keep it because a copy-paste link is a growth loop; the security cost lands on the user's Google/WhatsApp account.

## Strlix solution (concrete UX + IA)
Sharing lives **inside the phone**, as a system-level surface, not a dashboard button.

1. **Share sheet = Phone-OS overlay.** Long-press the floating Strlix pill → "Share this phone". Modal is a capability builder, not a toggle:
   - **Role**: `View only` (default) · `Control` · `Control + clipboard/file`
   - **Expires**: 15m · 1h · 8h · custom (max 7d; no "never" option exists in the UI)
   - **Max viewers**: 1 (default) / N
   - **Recipient lock**: `Anyone with link` requires a 6-digit passcode auto-generated and shown separately; `Email/phone-bound` sends a magic code.
   - **Blackout zones**: AI-in-phone suggests "Hide notifications & SMS app" — checked by default. Blacked regions are masked **server-side before encode**, so the pixels never leave the host.
2. **Watermark is non-optional on shared sessions.** Diagonal tiled overlay: viewer identity (email or `guest-a3f1`), share ID, UTC timestamp, refreshed every 30s, composited into the video stream server-side. Screenshot/screen-record of the guest still carries it. Owner's own session is unwatermarked.
3. **Guest chrome.** Guest sees a persistent top bar: "Shared by X · view-only · expires in 42:10" + a red dot when the owner is watching. Control requests use a **handoff token**: guest taps "Request control", owner gets an in-phone toast with 20s timeout; control auto-returns on 60s idle.
4. **Live revoke + audit.** Phone Settings → *Active shares*: each row shows viewer, IP/geo, frames streamed, and a **Kill** button that tears the WebRTC/WS peer within one RTT. Every event → append-only `share_events` log, exportable.
5. **Safety interlocks.** While any share is live: OTP/SMS notification content is masked, "Add payment method" and Strlix account-settings screens force-blur, and installing APKs requires the owner's device. Links die automatically on password change or plan downgrade.

## Android 7+ / graceful degradation notes
- Guest viewer targets Chrome 60+/WebView: if WebRTC/H.264 unavailable, fall back to the existing MJPEG-over-WS path at 10fps — watermark and blackout are already baked into frames, so security parity holds.
- No WebCrypto? Passcode verification is server-side; client never needs it.
- Low-RAM/2G: auto "view-only, 480p"; control mode is hidden rather than broken.
- No JS / link opened in an in-app browser: static page with expiry + "open in browser" — never an open stream.

## Acceptance criteria
- No UI path can create a share without an expiry; server rejects `exp > 7d` and any token lacking `exp`.
- A guest screen-recording contains a legible watermark with their identifier and share ID; blacked-out regions are absent from the raw stream bytes (verified by capturing server output, not DOM).
- Killing a share terminates the guest socket in <1s and all subsequent ticket exchanges return 410.
- View-only guests' pointer/key events are dropped server-side (input_gate unit test), not merely disabled in the client.
- With a share active, SMS/OTP notification bodies and account-settings screens are masked in the encoded stream.
