## Mistake restated

Competitors ship a **desktop browser with a spoofed Android fingerprint** (UA, WebGL, touch events) and sell it in the "cloud phone" category. There is no ARM Android userspace, so no APK install, no Play Store, no native TikTok/WhatsApp, no real sensors. Buyers discover this only after purchase. It persists because browser containers cost a fraction of ARM phone farms, and marketing copy says "Android profile" where buyers read "Android device."

## Strlix solution (concrete UX + IA)

1. **Two hard-separated catalog roots.** IA top-level: `/devices` (real ARM Android) and `/profiles` (browser antidetect). No shared listing grid, no shared search index, no cross-category filter. A `/profiles` listing cannot render the word "phone" — enforced by a lint rule on the catalog JSON.
2. **Capability badge as the primary card element**, not a spec footnote. Three machine-verified booleans per SKU: `apk_install`, `play_services`, `os_stream`. Rendered as ✅/❌ chips above the price. `❌ APK install` on every browser profile card.
3. **"Prove it" live probe.** Every ARM device card has a **Try live (60s)** button that opens the real OS stream from desktop-api `:8789` — the buyer sees the Android launcher, opens Settings > About, and the build fingerprint is shown in-stream. The probe result (`getprop ro.product.model`, `ro.build.version.release`, `pm list packages | grep vending`) is captured server-side hourly and stamped on the card as *Verified 2h ago*.
4. **AI lives inside the phone.** The assistant is an on-device overlay (floating bubble in the stream, not a sidebar chat). Ask "install TikTok" → it drives the actual launcher. On a `/profiles` SKU the bubble is absent, and hovering the disabled slot says "AI agent requires an OS stream."
5. **Honest browser upsell.** `/profiles` pages carry a persistent banner: "This is a browser profile. It cannot run Android apps. Need native apps? → Devices." One click, cart preserved.

## Android 7+ / graceful degradation notes

- Stream client negotiates **H.264 baseline** first; falls back to MJPEG-over-WS when WebRTC/`VideoDecoder` is missing (Android 7 WebView, old Chrome).
- Capability chips and probe data are **server-rendered HTML** — the honesty layer never depends on JS.
- Try-live unavailable (no codec / no capacity) → button becomes **"Watch 20s recorded probe"** (looping WebM/GIF of the same fingerprint check), never silently hidden.
- Touch-first: chips wrap to 2 columns ≤360px; no hover-only disclosure.

## Payment notes

Stripe + Razorpay in **test mode only**, stub keys, no live charges. Checkout interstitial repeats the three capability booleans and requires an explicit checkbox: *"I understand this SKU cannot install APKs"* — shown **only** for `apk_install: false` SKUs, so it never becomes banner blindness on real devices.

## Acceptance criteria

- A `/profiles` SKU renders `❌ APK install`, `❌ Play Services`, `❌ OS stream` and cannot appear in `/devices` search results.
- CI fails if any `/profiles` catalog entry contains "phone", "device", or "Android app" in title/description.
- Every `/devices` card shows a probe timestamp <24h old, sourced from live `getprop` via desktop-api `:8789`.
- Try-live delivers a visible Android launcher within 8s, or degrades to the recorded probe — never a blank player.
- Checkout for `apk_install: false` blocks until the acknowledgement checkbox is ticked (test-mode payment only).
