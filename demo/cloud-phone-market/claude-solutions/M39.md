## Mistake restated
The competitor's Purchase FAQ has an entry for "I have multiple unpaid orders and can't place a new one" — normalizing a state where a user's cart/checkout is blocked by orphaned pending orders. Cause: payment provider webhooks arrive late or never, each "Buy" click mints a new order row, and there's no idempotency key or TTL reaper. User cannot buy (revenue loss) and must open a ticket. Self-service recovery is absent.

## Strlix solution (concrete UX + IA)
**Principle: an order is never a blocker. At most one live checkout intent per (user, plan), auto-expiring.**

1. **Idempotent intent.** Buy button sends `Idempotency-Key = sha256(userId|planId|deviceRegion|bucket5min)`. Server upserts: existing `pending` intent within TTL is *returned*, not duplicated. Clicking Buy 6× yields one order.
2. **TTL reaper.** Pending orders expire at 15 min (`expires_at`), swept every 60 s → status `expired`, never counted against new purchases. Expired ≠ failed; UI says "Checkout window closed — start again" with a one-tap Retry.
3. **Never block.** New checkout is always permitted. If prior pendings exist, we show a non-modal top sheet: "2 earlier checkouts still confirming — we'll cancel them automatically if unpaid." No gate, no FAQ.
4. **Phone-first surfacing.** The phone canvas stays primary; billing appears as an in-phone bottom sheet over the stream (not a separate chat/web page). A **Payments pill** on the phone's status strip shows `⏳ confirming` with a live countdown; tapping opens *Orders* sheet listing each pending with **Recheck now** (forces provider poll) and **Cancel**.
5. **Poll, don't trust webhooks.** Client polls `GET /api/orders?status=live` every 3 s while a pending exists (backoff to 15 s); server also reconciles by polling the provider on read. Webhook is an optimization, not the source of truth.
6. **AI inside the phone.** The in-phone assistant overlay detects ≥2 pendings and offers one action chip: "Clear stuck checkouts" → calls cancel-all, then reopens checkout. No ticket path in the UI.
7. **IA:** remove the FAQ entry entirely; replace with `Account → Orders` (Live / History tabs) reachable from the phone status strip and profile.

## Android 7+ / graceful degradation notes
- Chrome 60 target: no `dialog`, no `:has()`, no optional chaining in shipped bundle (ES2017 transpile); sheet = fixed div + translate3d.
- No WebSocket needed for orders — plain `fetch` polling; if `fetch` absent, XHR fallback.
- No countdown animation on low-end: `prefers-reduced-motion` and `deviceMemory<2` → static "expires in ~14 min".
- If the phone stream falls back to MJPEG/still frames, the Payments pill renders in the HTML chrome above the canvas, not composited into video.
