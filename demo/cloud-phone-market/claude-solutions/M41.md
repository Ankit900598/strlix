## Mistake restated
Competitor app catalogs let a user launch any APK on any OS image (Android 7→15) with no per-app compatibility signal. Result: install fails (minSdk/targetSdk/ABI), or it installs but breaks at runtime (WebView behavior changes, scoped storage, background limits, 16KB page size on 15). Competitors skip it because a full app×OS matrix looks like manual curation work.

## Strlix solution (concrete UX + IA)
Compatibility is **derived, not curated**. Three cheap signals, merged:

1. **Static extract** — on APK ingest, parse `minSdkVersion`, `targetSdkVersion`, `maxSdk`, native ABIs, `requestLegacyExternalStorage`, `usesCleartextTraffic`, WebView/GMS deps. Gives hard green/red for most rows with zero human effort.
2. **Telemetry rollup** — every session already runs on a known image. Log `launch_ok`, `crash<10s`, `install_fail(reason)` keyed by `(package, sdk, abi)`. After N≥20 sessions a cell flips from "inferred" to "observed" with a success %.
3. **Rule pack** — ~30 hand-written heuristics for the known cliffs (scoped storage @29, exact alarms @31, foreground-service types @34, 16KB pages @35, cleartext @28). Cheap, versioned JSON, not a per-app matrix.

UX, phone-first:
- **OS chip row on the app card**: `7 8 9 10 11 12 13 14 15` — each chip green / amber / red / grey(unknown). Tap a chip → one-line reason: "Amber on 15 — uses legacy storage; files may not appear in Downloads."
- **Recommended pill** pre-selected on the best OS; Install button reads **"Install on Android 11 (recommended)"**. Overriding is always allowed — never block, warn with a bottom sheet + "Install anyway".
- **In-phone AI**: the assistant lives inside the phone shell as a floating bubble. On install failure it reads the real logcat/pm error and offers a one-tap **"Retry on Android 11"** which clones the session to the compatible image and re-installs, preserving the app queue.
- **Already-running mismatch**: a slim amber banner inside the phone frame, not a modal.
- **IA**: `/app/:pkg` gains a `Compatibility` tab (matrix, reasons, observed success %, "last verified" date). Grey = unknown, labeled honestly as "not tested yet" — never fake green.

## Android 7+ / graceful degradation notes
- The **market UI itself** targets Android 7 browsers: chip row is flex + CSS, no container queries; verdicts ship server-rendered so no-JS still shows colors + text labels (`OK` / `!` / `×`) — color is never the only channel (colorblind + old-screen safe).
- `unknown` is a first-class state; a missing telemetry backend degrades to static-only verdicts, never to a blank card.
- If aapt2 parse fails, the app is still installable with a "compatibility not analyzed" note.
- Chips are 44px touch targets; matrix tab collapses to a vertical list under 360px.

## Payment notes
Not relevant to compatibility itself, with one edge: a paid OS image tier (e.g. Android 15 on newer host) must not be billed when the install fails compat. Stripe/Razorpay stay in **test mode**; failed-compat sessions emit a `void_test_charge` stub and never call a live charge path.

## Acceptance criteria
- Every app card renders a 9-chip OS row with a non-null verdict per SDK; unknown is shown as grey "not tested", never as green.
- Install button defaults to the highest-verdict OS and states it in the label; override is possible in ≤2 taps.
- An `install_fail` inside the phone surfaces the in-frame AI bubble with a working "Retry on Android N" that re-installs on a compatible image without losing the queue.
- Verdicts come from the derived pipeline (aapt2 + rules + telemetry), with zero rows requiring manual per-app curation.
- Compat endpoints served on existing :8789; the video/WS stream path is byte-identical to today.
