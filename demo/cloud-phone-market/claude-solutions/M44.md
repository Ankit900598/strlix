## Mistake restated
Competitors let you boot a cloud phone, install an app, then wall you at the first OTP: the phone has no usable number, and SMS receive is a separate SKU/pool bought elsewhere. Users discover this mid-signup, when intent is highest and patience lowest — a pure onboarding cliff. It persists because inbound SMS is expensive per-number and a fraud magnet, so vendors quarantine it behind a paywall instead of underwriting it.

## Strlix solution (concrete UX + IA)
Principle: **every Strlix phone ships with a real inbox from minute zero**, and the cost/fraud problem is handled by *scope*, not by a surprise SKU.

1. **Bundled Starter Inbox.** Each new device gets 5 free inbound OTP receives on a shared rotating number, plus unlimited *BYO-number* forwarding. Shown at device-create time, never later: the create sheet has a line "Includes: SMS inbox · 5 OTP receives · +1 more on device verify."
2. **SMS lives inside the phone, not in the web console.** A preinstalled `Strlix Inbox` app on the Android home screen. OTP codes appear in the notification shade of the streamed phone exactly like a real device; `Tap to autofill` injects the code into the focused field via an accessibility-service shim. No copying between browser chrome and stream.
3. **In-phone AI does the work.** The floating Strlix assistant bubble detects an OTP field (heuristic: `inputType=number`, hint matches `/otp|code|verify/i`) and offers "Wait for code → autofill". It polls the inbox and fills; if quota is exhausted it does not throw a paywall — it offers three ranked fallbacks in one sheet: (a) **use your own phone** — QR to forward the SMS from your real handset, free forever; (b) **email OTP** if the app supports it; (c) **+1 receive** for a token.
4. **Quota is ambient, never a surprise.** Inbox app header shows `4 of 5 receives left`. A persistent quiet notification at 1 remaining. Console device card mirrors the same counter.
5. **Fraud containment instead of paywall.** Free receives restricted to a verified-sender allowlist (banks/major apps), one number per account, 60s cooldown, no international premium. Abuse → number rotates, account not banned mid-flow.
6. **IA:** `/market` → `/device/:id` (stream) → in-phone `Inbox` app; console route `/device/:id/inbox` is a read-only mirror for accessibility, not the primary path.

## Android 7+ / graceful degradation notes
- minSdk 24: no Autofill Framework (API 26). AccessibilityService `ACTION_SET_TEXT` is the 7.x path; on 26+ prefer `AUTOFILL_HINT_SMS_OTP`.
- No `SmsRetriever` assumption — codes arrive server-side, so app-hash mismatch is irrelevant.
- If accessibility is denied: degrade to a persistent notification with the code + a big copy button; assistant says "tap to copy, then paste".
- No SSE (old WebView / proxy): fall back to 3s polling on `/sms/latest`.
- Stream disconnect: codes persist 10 min server-side, replayed on reconnect.

## Payment notes
`+1 receive` and quota top-ups use the existing test-mode stub: Stripe `pk_test_` / Razorpay test key, `STRLIX_PAYMENTS_MODE=test`, all intents return synthetic success with a visible `TEST MODE — no charge` ribbon. Never block an in-progress OTP on payment: grant the receive optimistically, settle after.

## Acceptance criteria
- A brand-new device can complete a WhatsApp/Gmail OTP signup with zero purchases and zero console↔phone copy-paste.
- Quota remaining is visible before the first OTP is requested, not after.
- Exhausted quota shows the 3-option fallback sheet with BYO-number free path first; paywall is never the only exit.
- Autofill works on Android 7.0 via accessibility, and degrades to copy-button notification when the service is off.
- No real charge is possible: all payment paths assert test-mode keys and render the test ribbon.
