## Mistake restated
BrowserStack-style "switch device" tears down the session and hands the user a factory-clean device: app reinstalled at first-run state, logins gone, deep link lost, clipboard/files gone. The user must re-do 10 manual steps just to get back to the screen they were debugging. It persists because real-device pools are shared and sticky sessions waste scarce hardware — vendors optimize for device utilization, not for the human's mental context.

## Strlix solution (concrete UX + IA)
**Session ≠ Device.** A Strlix `Session` is a portable object (app set, accounts, files, deep-link cursor, AI transcript, script log). A `Device` is a rented runtime it attaches to. Switching device = re-attach, not restart.

1. **Hand-off Capsule** (auto, every action): on each AI/user step we append to a replayable `StepLog` (install apk, launch intent, adb keystrokes, fs writes, account tokens via encrypted `AccountVault`). On switch we snapshot: installed packages + versions, `/sdcard/Strlix/` working dir, per-app `run-as` data for debuggable apps, current `Activity` + intent extras, clipboard, screen orientation, locale.
2. **Switch sheet (phone-first)**: bottom sheet over the live stream, not a new page. Rows = target devices with a **"Context carry" badge**: ✅ Full (same/newer API, same ABI) · ⚠️ Partial (ABI/API delta — apps reinstall, logins carry) · ⛔ Fresh (no carry, explicit confirm).
3. **Warm hand-off**: target device provisions in the background while old stream still plays. Old device only released after the new one reaches "Restored." Progress is an in-phone overlay: *Installing 3 apps → Restoring files → Re-login → Reopening Checkout screen*. No full-screen spinner blocking the stream.
4. **"Resume where I left off"** chip lands the user on the exact Activity, with a ghost outline of the last tapped element.
5. **AI lives inside the phone**: the assistant bubble persists across the switch and states, "Carried 3 apps and your test login. Google Pay couldn't carry (device attestation) — tap to re-login." Any non-carryable item becomes a tappable repair task, never a silent loss.
6. **Rewind fallback**: if restore fails, "Replay steps 1–9" re-runs the StepLog headlessly (~seconds) rather than making the user retap.
7. **Pool-friendly**: capsule is stored server-side, so the old device returns to the pool within ~2s of hand-off. Sticky sessions are never needed.

## Android 7+ / graceful degradation notes
- API 24–25: no `pm install --user` niceties, no per-app backup keys → fall back to `adb backup`-free path: reinstall APKs + push `/sdcard` only; mark logins as Partial.
- Non-debuggable apps: `run-as` blocked → private data cannot carry; UI shows ⚠️ and offers StepLog replay instead of silent loss.
- ABI mismatch (arm64 → x86 emulator): re-resolve split APKs; if unavailable, ⛔ Fresh with reason shown.
- Scoped storage (API 29+): use MediaStore/SAF for `/sdcard/Strlix/`; on 7–9 use direct paths.
- Low bandwidth: capsule transfers device→server→device, never through the browser; if the socket drops, restore continues server-side and the overlay reconnects via SSE.

## Acceptance criteria
- Switching from Device A to Device B with 3 installed apps and 1 logged-in test account lands on the same Activity with apps installed and login intact in ≤20s, with the old stream visible until the new one is ready.
- Device A is released back to the pool within 2s of hand-off completion (verified via pool metrics), i.e. no sticky reservation.
- Any item that cannot carry appears as an explicit, tappable repair task in the in-phone AI bubble — zero silent losses.
- A failed restore never strands the user: the "Replay steps" fallback reproduces the StepLog, or the session returns to Device A unchanged.
- On an API 24 target, the sheet shows ⚠️ Partial with a plain-language reason before the user commits.
