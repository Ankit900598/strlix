## Mistake restated

Competitors advertise a wide Android matrix (8.1–15) for the *hosted image*, but the **viewer** is a single modern-Chrome path: WebCodecs + WebTransport/WebRTC-insertable-streams + WASM SIMD + OffscreenCanvas. On an Android 7/8 stock browser, Chrome 6x, UC/Opera Mini, or a locked-down corporate WebView, the page either white-screens or silently drops to 2 fps with no message. The claim fails at the client, not the cloud, and old-browser QA gets cut every sprint.

## Strlix solution (concrete UX + IA)

**1. Capability probe before the phone renders.** `capabilities.js` runs a ~120 ms synchronous-ish feature check (WebCodecs `VideoDecoder.isConfigSupported`, MSE `MediaSource.isTypeSupported('video/mp4;codecs=avc1.42E01E')`, WebRTC, WASM, `createImageBitmap`, PointerEvent, WebSocket binary) and picks a **tier**, stored in `localStorage.strlix_tier` with a manual override.

| Tier | Requires | Transport | Typical |
|---|---|---|---|
| **T0 Realtime** | WebCodecs + WebRTC | H.264 via WebRTC datachannel/track | Chrome 94+, modern |
| **T1 Stream** | MSE + WebSocket | fMP4 segments over WS, 300 ms buffer | Chrome 60–93, old Samsung Internet |
| **T2 Frames** | Canvas2D + WS binary | server-side JPEG diff tiles, 8–12 fps | Chrome 45+, Android 5–7 WebView |
| **T3 Snapshot** | `<img>` + form POST | 1–2 fps polled JPEG, tap = POST coords, no JS features | UC Mini, proxy browsers, KaiOS-ish |

**2. Phone-first UI stays identical across tiers.** Same device frame, same bottom dock (Home / Back / Recents / AI). Only the *pixels pipeline* changes. Never route a degraded user into a different "lite site" URL — same route, same IA.

**3. Honest tier badge inside the phone chrome.** A small pill above the device: `Realtime` / `Stream · 300ms` / `Frames · 10fps` / `Snapshot`. Tapping opens a sheet: what your browser supports, what's missing, "Try higher tier anyway" button, and "Why is this slow?" with the exact failing capability named (`WebCodecs unavailable`).

**4. AI inside the phone, degraded too.** The AI agent is a floating in-phone bubble that drives the device server-side (it sends input events to the emulator, not to the browser). So on T2/T3 the AI is *the recommended input method* — the UI flips copy to "Typing is laggy here — ask the assistant to do it." AI panel is plain HTML form + server-rendered transcript on T3, no streaming tokens.

**5. Marketing honesty at the buy point.** The device catalog card shows `Android 8.1` **and** a live "Your browser: Frames tier" chip so the buyer never pays expecting realtime. Checkout shows the same chip.

**6. Input degradation.** T0/T1: pointer events, 60 Hz coalesced. T2: throttled tap/swipe at 20 Hz, no multitouch pinch (offer on-screen zoom buttons). T3: click-on-image coordinate POST + an on-screen key pad and text field submit.

## Android 7+ / graceful degradation notes

- **Never white-screen.** `index.html` ships a server-rendered phone frame + static screenshot; JS upgrades it. If JS throws, the static frame and a `/snapshot` link remain.
- Transpile T2/T3 paths to **ES5**, no optional chaining, no `async/await` (Android 7 WebView = Chrome 51–58 depending on updates).
- Avoid `ResizeObserver`, `IntersectionObserver`, CSS `gap` in flex, `:is()`, custom properties in the legacy CSS bundle.
- Cap T2 tile encode server-side, not client-side — old devices are CPU-poor, keep decode to plain `drawImage`.
- WebSocket binary is supported back to Chrome 15; prefer it over anything exotic. Fall back to long-poll only in T3.
- Log tier + UA + failing capability to a beacon so "old-browser QA" becomes free real-world data instead of a paid device lab.
- Add 4 legacy rows to CI via BrowserStack matrix; failing the T2 smoke test blocks release.

## Payment notes

Checkout runs **Stripe test mode** (`pk_test_…`, card `4242…`) with a Razorpay test-key stub behind the same `POST /api/checkout/session`. No real charges. Stripe Elements needs a modern browser, so on T2/T3 the checkout falls back to a **server-rendered Stripe Checkout redirect** (plain form POST, works on Android 7). Order confirmation is server-rendered HTML, not a client-side toast.

## Acceptance criteria

- On a stock Android 7.0 WebView (Chrome 58) the marketplace loads, a device boots, and the user can tap/type at ≥8 fps in T2 — verified in CI, not manually.
- With JavaScript fully disabled, `/` renders the catalog and `/snapshot/:id` renders a controllable 1–2 fps device; no blank page anywhere.
- The tier badge is visible before purchase and names the exact missing capability when tapped; catalog cards show the buyer's tier chip.
- Forcing `?tier=t3` on modern Chrome produces a working session, proving the fallback path is exercised by developers daily.
- A test-mode Stripe purchase completes end-to-end on Chrome 60 via the redirect checkout with zero real charge.
