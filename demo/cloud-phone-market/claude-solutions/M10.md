## Mistake restated
While a cloud phone session is provisioning (cold boot, image pull, GPU node assignment), the wait screen plays a promotional/ad video instead of real provisioning state. The user loses the only signal that matters — is it working, how long left, what's blocking — so a 40s honest wait feels like a 3-minute scam. It persists because idle boot time is cheap, guaranteed-attention ad inventory on free/trial tiers.

## Strlix solution (concrete UX + IA)
**Rule: the boot screen is the phone, not a billboard.** The provisioning surface renders a 1:2.1 phone frame at final device resolution, so the stream fades in *in place* with zero layout shift.

Inside the frame, a **Boot Ladder** — 5 named stages streamed from the backend, each with a real timestamp as it completes:
1. Reserving device (`pixel-7a / in-blr-3`) → 2. Attaching your storage (`profile: "main", 4.2 GB`) → 3. Cold-booting Android 13 → 4. Restoring apps (`7 of 12`) → 5. Opening stream.

Around it:
- **ETA band, not spinner**: "≈ 34s left" from a p50/p90 estimate per node class; if actual overruns p90, the copy flips to "Slower than usual — 20s more, or [Switch node]". Never a fake progress bar; the bar only moves on server events.
- **Queue transparency** for free tier: "You're #3 in the free queue. Free devices boot when one frees up — usually 1–4 min." Plus a **test-mode** "Skip the queue" upsell as a *dismissible inline row*, never a full-screen interstitial, never a video.
- **Warm-start pool**: paid tiers get a pre-booted device; the ladder collapses to a 2s "Attaching storage".
- **Useful wait, not ads**: the frame's lower third offers *your own* pending actions — "Queue an install: [WhatsApp] [Telegram]" — which are executed by the in-phone AI agent the instant boot finishes. Wait time becomes setup time.
- **AI stays inside the phone**: no chat panel outside the frame. The agent surfaces as a floating pill *within* the device frame after boot ("Installing 2 queued apps…").
- **Failure is a state, not a loop**: on timeout → "Node in-blr-3 didn't respond. Retrying on in-blr-1 (attempt 2 of 3)" with a Cancel that actually cancels and refunds trial minutes.

## Android 7+ / graceful degradation notes
- SSE over `fetch`+`ReadableStream` is unreliable on Android 7 WebView (Chrome 51-ish); use `EventSource` where present, else **3s polling** of `GET /provision/status` — identical JSON shape, one adapter in `provision.ts`.
- No `backdrop-filter`, no CSS `@property`; stage transitions use `opacity`/`transform` only, `prefers-reduced-motion` respected.
- If WebRTC negotiation fails, fall back to MJPEG on the same `:8789` path and label it honestly: "Low-bandwidth mode — 12 fps, touch only."
- Boot ladder is plain DOM + `aria-live="polite"` so it works with JS-lite rendering and screen readers.

## Payment notes
Only the "Skip the queue" row touches payment. Stripe/Razorpay **test keys only** (`pk_test_…`), `STRLIX_PAYMENTS_MODE=test` gates the button; server rejects any non-test key. A visible "TEST MODE — no card is charged" badge sits on the checkout sheet. Trial minutes are refunded server-side on provisioning failure.

## Acceptance criteria
- Zero video/ad elements render on any provisioning surface; `boot-no-ads.spec.ts` fails the build if a `<video>` or ad-slot node appears in the boot tree.
- Every progress advance is caused by a server event; with the backend stalled, the bar and ETA visibly stall too (no synthetic creep).
- Stream fades in with no layout shift — measured CLS < 0.02 across boot→stream transition.
- On Android 7 WebView with `EventSource` stubbed out, the polling path shows all 5 stages and a correct ETA.
- Overrunning p90 swaps in the "Slower than usual" copy with a working Switch node / Cancel within one poll interval.
