## Mistake restated
Competitors bolt AI onto the *host page*: an AIGC sidebar, a prompt box next to the stream, or an RPA script builder outside the device. The user's mental model becomes "I'm operating a remote machine from a cockpit," not "this is my phone." Every AI action then requires leaving the phone surface, and AI becomes a separately-billed seat feature rather than part of the OS.

## Strlix solution (concrete UX + IA)
**Rule: zero AI chrome outside the device rect.** The market page has exactly one interactive surface — the phone. No sidebars, no prompt bar, no "Agent" tab.

1. **Strlix Assist lives as a system surface inside the frame.** Long-press the home pill (or swipe up-and-hold, Android gesture parity) → an in-phone sheet slides up *within the device viewport*, rendered by an overlay compositor layered on the stream canvas, styled as Android Material 3 bottom sheet. It looks like Assistant, not a web widget.
2. **Input is phone-native.** Voice via device mic route (WebRTC audio track sent into the VM), text via the phone's own IME. The host page never focuses a DOM input while the phone is active — keystrokes are injected as Android key events.
3. **AI acts by driving the phone, visibly.** Assist executes as UIAutomator-style taps/swipes replayed on the stream at human pace with a soft touch-ripple, so the user *watches their phone do it*. No hidden RPA log. A floating in-phone "Stop" chip cancels.
4. **Results land in phone apps**, not download panels: generated image → Photos; generated caption → clipboard + share sheet; script → Strlix Routines app (an in-phone app icon, not a web page).
5. **IA:** `/` market grid → `/phone/:id` full-bleed device. Only host-level UI: device chrome, connection pill, exit. Everything else is an app icon or system surface inside Android.
6. **Degradation:** if the overlay compositor can't run, Assist still opens as a real in-VM app (`com.strlix.assist`) — same UI, server-rendered into the stream. Identical pixels, so users never learn there were two paths.

## Android 7+ / graceful degradation notes
- Android 7 has no gesture nav → Assist trigger = long-press the on-screen **Recents**/home softkey; overlay listens for that key event, no OS change needed.
- No `SYSTEM_ALERT_WINDOW`-style client compositing on old WebViews → host-side canvas overlay is the primary path; in-VM APK is fallback for API 24–25 where accessibility injection is limited.
- Mic missing/denied → sheet shows keyboard-only mode via device IME; never a host `<input>`.
- WebGL absent → 2D canvas MJPEG from :8789 at 12fps; overlay is DOM, unaffected.
- Reduced motion → action replay skips ripples but keeps pacing.

## Acceptance criteria
- DOM audit on `/phone/:id`: no AI-related element exists outside the device rect bounding box.
- Assist is reachable only via an in-phone gesture/icon; no host keyboard shortcut or toolbar button.
- Every AI action produces visible touch events on the stream; a user watching muted can narrate what happened.
- With overlay disabled (`?assist=invm`), Assist renders from the in-VM APK with visually equivalent layout.
- On Android 7 / no WebGL / mic denied, Assist still opens and completes a text-only task.
