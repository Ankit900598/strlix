## Mistake restated
Competitors ship the antidetect browser and the cloud phone as two products: two logins, two dashboards, two subscriptions, two proxy pools, two fingerprint editors. Users running a mobile+desktop identity for one account must context-switch and pay twice, and the two profiles drift (proxy in browser ≠ proxy in phone), which is itself a detection signal. It persists because the browser and phone came from different teams/acquisitions with separate P&Ls.

## Strlix solution (concrete UX + IA)
**One object: the Identity.** Not "a browser profile" and "a phone". An Identity = `{persona, proxy, geo/locale/timezone, cookies/tokens, devices[]}`. A device is a *surface* of the Identity: `android` (cloud phone) or `desktop` (antidetect browser session). Same proxy egress IP, same timezone, same locale — enforced, not copied.

IA (single app, phone-first, 3 tabs at the bottom):
1. **Phones** — grid of running Identities as phone cards (live thumbnail from :8789 stream). Tap → full-screen phone. This is the default and the home.
2. **Identities** — list; each row shows persona name, proxy badge, and two surface chips: `📱 Android 11` / `🖥 Chrome 122`. Chip tap = launch that surface. A greyed chip means "not created yet" → tap creates it inheriting proxy/geo/locale from the Identity (zero re-entry of fingerprint data).
3. **Wallet** — one balance, one plan.

Inside the phone (AI is *in* the phone, not an outside chat panel): a floating Strlix bubble over the Android surface. Commands like "open this same account in desktop browser" spawn the desktop surface on the *same* Identity and hands back a `strlix://surface/desktop/<id>` deep link — the browser opens as a second card in the same Phones grid, so there is no second portal to visit.

Cross-surface continuity: **Handoff**. Long-press a phone card → "Continue on desktop". Cookies/localStorage for the target domain are transferred through the Identity store (not scraped from the device), so a session started on the phone resumes in the browser with the same IP.

Billing: one subscription, metered in **Identity-hours**, surface-agnostic. Android hour = 1.0 credit, desktop browser hour = 0.6. Never two invoices. The Wallet shows a single burn-rate line broken down by surface, not by product.

Anti-drift guard: editing proxy/timezone on an Identity shows "affects 2 surfaces" and restarts both; you cannot set them per-surface.

## Android 7+ / graceful degradation notes
- Target web UI runs in Chrome 60+/WebView on Android 7: no CSS container queries, no `:has()`; flex + media queries only.
- Stream: WebCodecs if present, else MJPEG-over-WS fallback at 10fps, 480p on `deviceMemory <= 2`.
- Live thumbnails in the grid throttle to 1 frame/2s on `navigator.connection.effectiveType` of `2g`/`3g`; static last-frame JPEG if hidden.
- No `backdrop-filter` (jank on Mali GPUs) — solid surfaces.
- AI bubble is a plain fixed-position div, draggable via `touchstart/move`, no pointer events.

## Acceptance criteria
- Creating a desktop surface on an existing Identity requires **zero** fingerprint/proxy re-entry and yields the same egress IP as the Android surface (verified by an in-app IP check on both).
- Android and desktop surfaces appear as cards in the **same** grid; there is no second URL, login, or dashboard anywhere in the app.
- Editing proxy or timezone at Identity level updates both surfaces; per-surface override is not exposed in the UI or the API.
- Wallet shows exactly one balance and one test-mode subscription; a session using both surfaces produces one invoice with two line items.
- On an Android 7 WebView at 3G, the Phones grid renders within 3s and falls back to MJPEG without a blank canvas.
