## Mistake restated

Competitors meter three unbundled dimensions (power-on minutes, browser/profile seats, proxy GB) with a $0 idle rate as the headline. The user sees "$0 when off" but gets a bill assembled from three meters they never watched. Monthly cost is unpredictable before the invoice, so the only defense is paranoid manual power-off — which turns the product into a chore. It persists because each meter is a separate revenue lever.

## Strlix solution (concrete UX + IA)

**One meter: the Phone-Hour.** A phone costs hours while booted. Proxy, storage, automation runs, and AI actions are *included* in the phone-hour — no second meter. Plans are hour bundles (e.g. Starter 100h, Studio 600h), not seats.

1. **Wallet chip in the phone shell, always visible.** Top-right of the device frame: `142h left · this phone 0.8h/day`. Tapping opens the Usage sheet — never a separate billing site.
2. **Predicted month, not consumed month.** Usage sheet leads with "At current pace: **318h of 600h** by Oct 31" plus a per-phone bar list. Consumption to date is secondary. This is the anti-bill-shock primitive: the number that matters is the *forecast*.
3. **Hard ceiling, not overage.** When the bundle is exhausted phones suspend (state preserved, 30-day retention); they do not silently bill more. Optional "auto-extend +50h" toggle is off by default and shows the exact added cost before it can be turned on.
4. **Cost preview on every spend action.** "Boot phone" / "Run automation" / "Ask AI to do this" buttons carry an inline estimate: `Boot · ~0.2h`. Long-running automations show a live burn counter in the notification shade *inside* the phone.
5. **Idle autosleep is the default, and we say so.** Banner on first boot: "Phones sleep after 10 min idle. You are not billed while asleep." The competitor's $0-off rate becomes a default behavior rather than a trap.
6. **AI lives in the phone.** The assistant is a system app; when it proposes a task it quotes hours in the same confirm sheet as any manual action.

**IA:** `/phones` (grid + per-phone hour bar) → `/phone/:id` (stream + wallet chip) → `/usage` (forecast, per-phone breakdown, ledger) → `/plan` (bundle change, effective immediately, prorated in hours not dollars).

## Android 7+ / graceful degradation notes

- WalletChip and CostPreview are plain DOM over the stream canvas — no WebGL, no CSS `backdrop-filter` (falls back to solid `rgba` on Chrome 58).
- Forecast math runs server-side; client renders a number. No `Intl.NumberFormat` options beyond `maximumFractionDigits`.
- Usage bars use flex widths, not CSS grid subgrid or `container` queries.
- If the WS meter feed drops, the chip shows last-known hours with a dimmed dot rather than a spinner or a wrong number.
- Ledger list is paginated at 50 rows; no virtualization dependency.

## Payment notes

Test-mode only. `/plan` uses Stripe test keys (`pk_test_`) or Razorpay test stub; a `TEST MODE — no card charged` bar is pinned above the pay button. Bundle purchase credits hours locally via `meter.js`; webhooks are stubbed and idempotent by `event.id`. No stored PAN, no real charges.

## Acceptance criteria

- Every screen that can spend money shows an hours estimate before the action commits; zero spend paths lack a preview.
- Exhausting a bundle suspends phones and never produces a charge above the purchased bundle unless auto-extend was explicitly enabled.
- The UI exposes exactly one usage unit; no seat, proxy, or GB line item exists anywhere.
- Forecast on `/usage` is within ±10% of actual month-end hours in a replayed 30-day event fixture.
- Full flow (browse → boot → usage → plan) works on Chrome 58 / Android 7 with no console errors and no blank overlays.
