## Mistake restated

Competitors gate *useful* testing behind a local tunnel binary (Local Testing / Sauce Connect / ngrok-style). To tap a staging build once, a user must download a daemon, get a proxy allowlist through IT, resolve cert/MITM errors, and only then see a device. First tap is an hour away, and tunnel failures surface as opaque "device unreachable" errors. It persists because the security need is real (private origins must not be exposed), but the UX has never been treated as a product surface.

## Strlix solution (concrete UX + IA)

Principle: **the phone boots first, networking is a progressive upgrade — never a gate.**

1. **Tap-first boot.** Opening any device in the market streams a real Android phone in <10s with public internet egress. No tunnel, no download. Staging is an *unlock*, not a prerequisite.
2. **Reachability chip in the phone chrome** (top-right of the stream, not a separate dashboard): `🌐 Public` / `🔒 Private: staging-vpc` / `⚠ Partial`. Tapping it opens the Network sheet.
3. **Three unlock tiers in the Network sheet**, ordered by time-to-value:
   - **Paste-a-URL (0 min)** — user pastes `https://staging.internal`. Strlix DNS-resolves it from the device; if RFC1918/NXDOMAIN, we auto-suggest tier 2 inline rather than erroring.
   - **Hosts + header injection (30s)** — map `staging.internal → 203.0.113.9` and inject a bypass header/basic-auth. Covers most "staging is public but firewalled by header/IP" cases without any tunnel. Applied via device-level proxy config, no root.
   - **Strlix Link (2–5 min)** — one `curl | sh` or docker one-liner, copy-buttoned, that runs on the dev's laptop or a CI runner. Outbound-only WSS to :8789, no inbound ports, no IT ticket for the common case. A generated **IT one-pager** (egress host, port, SPKI pin, data-handling) is downloadable so the enterprise ask is a single email, not a discovery project.
4. **AI inside the phone.** The Strlix assistant runs as an on-device overlay bubble. When a page fails to load, it reads the device's own DNS/TLS/HTTP error and says: "`staging.internal` resolved to 10.0.3.4 — that's private. Want me to start Strlix Link? [Copy command]" It can apply the hosts entry and retry the tap itself. Diagnosis happens where the failure happened, not in a side chat.
5. **Link health is device state, not a separate console.** Killing the tunnel degrades the chip to `⚠ Partial` and the overlay offers reconnect; the session never dies.
6. **Team reuse.** A running Link is shareable to the org, so teammate #2 gets tier-3 access with zero setup.

## Android 7+ / graceful degradation notes

- Hosts mapping and proxy config are applied host-side (device VM network namespace), so no API-level dependency — works on Android 7 images identically to 14.
- Android 7 lacks user-CA trust for apps targeting 24+: detect `targetSdk ≥ 24` and offer **plaintext-HTTP passthrough** or a per-app network-security-config patch instead of silently failing TLS.
- No WebSocket in the browser (locked-down corp browser): fall back to long-poll control channel; stream degrades to 5fps JPEG, chip shows `Low-bandwidth`.
- No Link possible at all (airgapped IT refusal): tiers 1–2 still deliver a working phone; we never show a dead-end.

## Acceptance criteria

- Cold visitor taps a live Android device within 10s, zero downloads, zero account-less blockers.
- A public-but-header-gated staging URL loads via tiers 1–2 in under 60s with no binary installed.
- When a private host fails, the in-phone overlay names the actual cause (DNS/TLS/proxy) and offers a one-tap or one-paste fix — no generic "device unreachable".
- Strlix Link connects outbound-only to :8789 in ≤5 min from copy to green chip, and its loss degrades the session rather than ending it.
- Every tier works on an Android 7 image, or states the exact limitation and the supported alternative.
