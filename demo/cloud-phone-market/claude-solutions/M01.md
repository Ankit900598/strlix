## Mistake restated
VSPhone-class flows gate the product behind register → fund prepaid wallet → choose SKU → wait for provisioning (often after an ad/queue). First pixel of a working Android screen arrives minutes in, so users bounce before the "wow" moment. It persists because prepaid wallets suppress free-compute abuse and sunk-cost balances drive renewals.

## Strlix solution (concrete UX + IA)
**Instant Demo Phone: pixels in <3s, no account.**

1. **Landing = a phone, not a pricing table.** `/` renders a device frame that is already streaming. A warm pool of pre-booted Android containers (min 5 idle, autoscale) is claimed by anonymous session cookie; no provisioning wait. Skeleton frame + last-frame poster shows in <300ms while WebRTC/MJPEG connects to desktop-api `:8789`.
2. **Trial budget, not wallet.** 5 minutes free, anonymous. Countdown chip top-right ("4:12 free"). Abuse control = IP+fingerprint+Turnstile rate limit and a locked demo image (no Play sign-in, egress allowlist, no clipboard-out), not prepayment.
3. **AI is inside the phone.** A system-overlay bubble rendered *on top of the stream* (part of the device UI, not a side chat panel). Tap → command bar: "install TikTok", "set Indonesia proxy". Agent drives the same ADB/input channel the user does; every action shows as a toast inside the phone frame plus a reversible step chip.
4. **Progressive identity.** Nothing is asked until the user does something worth saving. At minute 5 (or on first app install / APK upload), a **bottom sheet over the live phone** — the stream keeps running blurred-free behind it — offers: "Keep this phone" → email/Google only. Session state (installed apps, login) is snapshotted and rehydrated into the persisted instance; the user never restarts from zero.
5. **Payment is the third step, never the first.** Free tier = 30 min/day persistent. Card only on upgrade (region, always-on, multi-device).
6. **IA:** `/` demo phone · `/p/:sessionId` resumable phone · `/apps` catalog (install button targets *your live phone*) · `/plans` · `/me/phones`.

## Android 7+ / graceful degradation notes
- Transport ladder: WebRTC H.264 → MJPEG over WS → 4fps JPEG polling. Android 7 stock WebView/Chrome 5x lacks reliable WebRTC insertable streams; feature-detect `RTCPeerConnection` + `VP8/H264` codec list, fall back silently.
- No ES2020 in the boot path: ship `boot.legacy.js` (ES5, no optional chaining) via `nomodule`; the phone must paint even if the modern bundle fails.
- Touch: pointer events with `touchstart` fallback; disable 300ms delay via `touch-action: none`.
- Low-end: auto-drop to 480×854@15fps if decoded-frame lag >400ms; show "Lite mode" chip, tappable to force HD.
- No WebSocket (proxy-blocked) → long-poll frames endpoint.

## Payment notes
Stripe + Razorpay in **test mode only**; `checkout-stub.ts` returns a mock `paymentIntent` and flips a local entitlement flag. No live keys in repo; `STRLIX_PAY_MODE=test` asserted at boot and a "TEST MODE — no charge" ribbon renders on `/plans`. No prepaid wallet primitive at all.

## Acceptance criteria
- Cold load on 4G, Android 7 device: first live Android frame visible in ≤3s, zero taps, zero account.
- Trial phone accepts touch input and an AI command ("install X") before any signup prompt appears.
- Signup sheet appears only at 5:00 or first install; accepting it preserves installed apps/state — no re-provisioning wait.
- Killing WebRTC support still yields an interactive phone via MJPEG/poll fallback.
- No code path can initiate a real charge; test-mode assertion fails the build if live keys are present.
