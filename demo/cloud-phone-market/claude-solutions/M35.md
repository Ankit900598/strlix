## Mistake restated
When WebRTC negotiation or H.264 decode fails, competitors show an infinite spinner or a black rectangle with no state, no cause, no fallback. The session is actually still alive server-side, but the user sees nothing, assumes their device/network is broken, and churns. It persists because teams instrument only the happy path, and the JPEG/scaffold fallback path — when it exists — is treated as a debug hack rather than a shipped, named product mode.

## Strlix solution (concrete UX + IA)
**Stream quality is a first-class, visible state machine inside the phone chrome — never a hidden failure.**

Five named modes, shown as a pill on the phone's top bezel (tap → detail sheet):
1. `LIVE HD` — WebRTC H.264, green dot
2. `LIVE SD` — WebRTC, downscaled/bitrate-capped, amber
3. `SNAPSHOT` — MJPEG/periodic JPEG over HTTP from :8789, ~2–4 fps, amber. Input still works (tap/swipe/type posted to control endpoint); only video is degraded.
4. `SCAFFOLD` — no pixels available: render last JPEG frame greyscale + live UI-tree overlay (from the accessibility/uiautomator dump) as tappable boxes. User can still press buttons and read text.
5. `PAUSED` — phone alive, stream stopped by user or idle-timer. Explicit "Resume stream" button, not a dead screen.

Degradation is **automatic and announced**: a one-line non-blocking toast on the phone glass — "Video dropped to Snapshot (network). Your phone is still running. Tap for details." Never full-screen modal, never blocking.

Detail sheet contents: current mode, why (ICE failed / decoder unsupported / bandwidth <N kbps / server GPU busy), what still works (checklist: touch ✓, keyboard ✓, file upload ✓, video playback ✗), and two buttons: **Retry HD** and **Stay in Snapshot**. Plus "Copy diagnostics" (session id, ICE state, codec, RTT) for support.

**AI inside the phone, not outside:** the in-phone AI assistant overlay stays functional in SCAFFOLD mode — because it drives the UI tree, not pixels. Copy: "Video is degraded, but I can still run tasks for you." This turns the failure into a differentiator: an agent-driven session survives a dead video pipe.

Never-black rule: the canvas always renders *something* — last frame, skeleton, or scaffold boxes. Spinner allowed max 6s, then auto-fallback.

IA: mode pill (bezel) → Stream detail sheet → Diagnostics → Support handoff.

## Android 7+ / graceful degradation notes
- Android 7 WebViews lack reliable H.264 hardware decode → detect via `MediaCapabilities`/canPlayType; if absent, boot straight to `SNAPSHOT`, skip the 6s spinner entirely.
- No VP9/AV1 assumptions; JPEG path is plain `<img>` swap (no canvas, no WASM) so it works on Chrome 51+.
- Scaffold overlay uses absolutely-positioned divs, no CSS grid gaps, `will-change` avoided (low RAM).
- Frame budget: cap JPEG poll at 3 fps and 720px wide on `navigator.connection.saveData` or `effectiveType` ≤ 3g.
- Touch input is posted independently of video transport, so input latency stays usable in every mode.

## Payment notes
Relevant only for entitlement honesty: if a paid "HD tier" session degrades to SNAPSHOT for >60s cumulative, auto-issue a **minute credit** (test-mode Stripe/Razorpay stub, no real charges) and surface "Credited 3 min — video was degraded" in the session summary. Never bill full-rate minutes spent in SCAFFOLD.

## Acceptance criteria
- Killing the WebRTC ICE path mid-session never yields a black screen or >6s spinner; UI lands in SNAPSHOT with a toast within 12s.
- Blocking both WebRTC and JPEG endpoints still renders tappable SCAFFOLD boxes, and a tap reaches the device.
- Mode pill and detail sheet always state current mode, cause, and what still works; "Retry HD" restores LIVE HD when the path recovers.
- On an Android 7 browser without H.264 decode, first paint is SNAPSHOT with no spinner stall.
- Degraded minutes on a paid tier produce a visible test-mode credit line in the session summary.
