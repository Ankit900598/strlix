## Mistake restated
Competitors forward raw touch events over the network and render nothing locally. On 80–250 ms RTT the user sees no reaction to their tap, assumes it was dropped, taps again — producing duplicate purchases, double-sends, wrong list items, and the feeling that the phone is "broken" rather than "far away". Vendors hide this behind marketing ("60 FPS gaming") instead of showing input state.

## Strlix solution (concrete UX + IA)
Local-first input feedback layer rendered in the browser canvas overlay, above the video, never waiting for the server.

1. **Instant ink (0 ms):** On `pointerdown` draw a 44 px ripple at the touch point in Strlix accent, opacity 0.35. This is pure client paint — it always appears even at 400 ms RTT.
2. **Pending → confirmed state machine:** ripple states `sent` (hollow ring, pulsing) → `acked` (fills, then fades 120 ms) → `lost` (ring turns amber, small "retry?" chip after 1.2 s). Ack comes from the stream's input-ack channel (frame seq echo from desktop-api :8789). If no ack in `2×RTT+80 ms`, mark lost.
3. **Ghost cursor for drag/scroll:** during `pointermove`, render the *local* finger path plus a translucent "server thinks you're here" dot lagging by measured RTT. Users learn the offset instead of fighting it.
4. **Double-tap suppression:** a second `pointerdown` within 350 ms and 32 px of an unacked tap is swallowed and shown as a "1×" badge on the existing ripple — the single most valuable fix for mis-purchases.
5. **Predictive scroll:** vertical flings are integrated locally and applied as a CSS `translateY` on the video element immediately, snapping back when the real frame arrives (max 240 px displacement, clamped so it never looks like tearing).
6. **Latency HUD (IA):** top-right pill shows `RTT 92 ms · good`. Tap opens *Connection* sheet: RTT sparkline, jitter, predicted-vs-actual error, and a **Input mode** toggle — `Responsive (prediction on)` / `Exact (raw forward)` for pixel-precise work like drawing apps.
7. **AI inside the phone:** when lost-input rate > 10 % over 30 s, the in-phone Strlix assistant bubble (bottom-right, inside the device frame, not a side chat) says: "Your network is dropping taps. Switch to 480p to cut latency?" with a one-tap action.

## Android 7+ / graceful degradation notes
- Overlay uses 2D canvas, not WebGL — works on Chrome 60 / WebView on Android 7.
- No `PointerEvent` → fall back to `TouchEvent` shim; no `requestAnimationFrame` throttle games, cap ripple at 30 fps.
- If the ack channel is unavailable (WS-only fallback), degrade to **optimistic mode**: ripple fades on a fixed 250 ms timer, dedupe still active — dedupe is the safety property and must never depend on acks.
- Low-end devices (<2 GB RAM): disable ghost cursor + scroll prediction, keep ripple and dedupe. Flag `perfTier=low` from `deviceMemory`/frame budget.
- `prefers-reduced-motion`: static dot instead of pulse.

## Payment notes
Not central. Relevant only in that tap dedupe protects the checkout flow: the Stripe/Razorpay **test-mode** stub must also carry an idempotency key per pointer-gesture id so a duplicated tap can never create two test charges.

## Acceptance criteria
- At simulated 250 ms RTT + 5 % loss, visible feedback appears within 1 frame (≤16 ms) of `pointerdown`, measured in a Playwright trace.
- Duplicate taps within 350 ms / 32 px of an unacked tap are never forwarded to :8789 (unit test on the dedupe window).
- Unacked taps surface an amber "lost" state within `2×RTT+80 ms` and offer retry; no silent drops.
- Exact mode disables all prediction and dedupe, verified by event-log equality with raw forward.
- On Android 7 WebView with no ack channel, ripple + dedupe still function; no console errors, no WebGL requirement.
