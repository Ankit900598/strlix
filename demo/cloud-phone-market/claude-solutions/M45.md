## Mistake restated
The REST API accepts rich fields on batch create (region, android_version, tags, proxy, ram/cpu tier, expiry, group, rooted flag, GPU mode), but the web UI exposes only a search box and 2–3 dropdowns. Ops teams end up scripting because the UI can't express what the API already models; UI users get a degraded, second-class view of their own fleet. It persists because the API is treated as the reseller/automation surface and the UI as a retail funnel, so nobody owns parity as a shipping requirement.

## Strlix solution (concrete UX + IA)
**1. Schema-driven UI, not hand-written forms.** The device/order schema is the single source of truth (`schema/device.schema.json`, served at `/api/v1/schema/device`). The market UI renders filters, batch-create form, and column chooser by iterating that schema. Adding an API field automatically adds a filter chip + a table column + a form input. No field can ship API-only.

**2. Parity guard in CI.** A test diffs `GET /api/v1/schema/device` filterable fields against the filter registry the UI builds. Missing field = red build, with an explicit `ui_hidden: true` escape hatch that requires a reason string (shown in `/dev/parity` page).

**3. Query bar with dual mode.** One control, two faces: chip mode (tap to add `region = sg`, `android >= 9`) and raw mode (`region:sg android:>=9 tag:warmup -status:expired`). Toggle is a single icon; the raw string is the URL (`?q=`), so it is shareable and scriptable.

**4. "Copy as API call" everywhere.** Any filter result or batch-create form has a `</>` button emitting the exact `curl` + JSON body. Reverse direction too: paste a curl/JSON into the query bar and the UI hydrates the form. This makes UI and scripts interchangeable instead of rival workflows.

**5. Saved views = server objects.** Saved filters live at `/api/v1/views`, so a script and the UI reference the same view id. Bulk actions (reboot, reinstall, extend, tag) apply to a view, not a hand-picked checkbox set.

**6. AI inside the phone.** The assistant lives in the phone shell overlay (bottom sheet on the device screen), not a separate chat column. "Find my expiring SG phones" fills the query bar and shows the resulting chips for confirmation before acting — AI writes the query, the human approves it.

## Android 7+ / graceful degradation notes
- Query bar raw mode is a plain `<input>`; chip mode needs no CSS `:has()` — use class toggles.
- No `URLPattern`, no `Array.prototype.at`; target ES2017 build for Chrome 60 WebView.
- Schema fetch failure → fall back to a bundled snapshot of `device.schema.json` and show a "filters may be stale" banner; never render an empty filter panel.
- Stream: WebSocket + H.264; if MSE unavailable, degrade to JPEG-frame polling at 5 fps with a "low bandwidth mode" chip.
- Table virtualizes above 200 rows; below that, plain DOM so old WebViews don't jank.

## Payment notes
Batch create shows a live cost preview computed from the same fields the API prices on (count × tier × days). Checkout uses Stripe/Razorpay **test keys only**; `CopyAsApi` on the order emits the order payload with a `"test_mode": true` flag. No real charges; webhook handler asserts test-mode event and logs.

## Acceptance criteria
- CI fails if any `filterable: true` schema field lacks a UI filter and a documented `ui_hidden` reason.
- Every field accepted by `POST /api/v1/devices:batch` is settable in the UI batch form, verified by an automated field-by-field test.
- Any UI filter state round-trips: URL → curl → API → same result set; and pasted curl → hydrated UI form.
- Saved views created in UI are usable by id from the API, and vice versa.
- Fleet page with 500 devices renders and filters under 2s on an Android 7 WebView with the bundled-schema fallback path active.
