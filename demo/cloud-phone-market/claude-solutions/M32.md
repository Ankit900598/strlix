## Mistake restated
Competitors list emulators/simulators and physical devices in one flat grid with near-identical cards. Users grab a cheap virtual device for a test that needs real silicon (camera, DRM, GPU, biometrics, telephony, thermals) — or overpay for a physical unit to run a UI smoke test. Wrong test conclusions, wrong bill. It persists because both SKUs are real revenue, and the UI expresses the difference as a small text label instead of hierarchy.

## Strlix solution (concrete UX + IA)
**1. Two classes are never siblings in one grid.** Top-level IA is a segmented rail: `Cloud Virtual` | `Real Metal`. Default landing = whichever the *task* requires, not "all devices". No mixed-class scroll list anywhere.

**2. Capability-first entry (the real fix).** Primary CTA is not "pick a device", it is "what are you testing?" — a chip row: Camera, DRM/Widevine L1, NFC, Fingerprint, SIM/Telephony, GPU benchmark, Sensors, Bluetooth, UI/regression, App install. Selecting a hardware-bound chip *disables the Virtual rail* with an inline reason: "Widevine L1 is unavailable on virtual devices — L3 only." Selecting UI/regression surfaces a savings nudge toward Virtual.

**3. Card differentiation by form, not badge.** Real Metal cards: photographic device render, dark slate surface, serial/rack ID, "Rack BLR-2 · unit #14", physical-availability queue. Virtual cards: flat wireframe glyph, teal surface, "spins up in ~8s", instance shape (vCPU/RAM). Different card height, different corner radius, different column count. Class name is always in the card title, not a corner pill.

**4. Inside-the-phone AI guard.** The floating in-phone assistant watches session events. If a session on a Virtual device calls `Camera2`, `MediaDrm`, `TelephonyManager#getSimState`, or `FingerprintManager`, a bottom sheet drops *inside the phone frame*: "This is emulated hardware — the result won't match production. Move to Real Metal (Pixel 8, ~40s handoff, keeps your APK + state)." One-tap migrate: same APK, same test data, session receipt links both runs.

**5. Truth banner + receipt.** Every session frame carries a persistent 24px class strip (teal "VIRTUAL — emulated hardware" / amber "REAL METAL"). Exported test reports embed the class; a virtual-run report is watermarked so it can't be cited as a device-certification result.

**6. Wrong-class refund.** If the AI guard fires within the first 120s of a Real Metal session that could have been Virtual, we auto-apply a credit — makes the hierarchy trustworthy rather than upsell-shaped.

## Android 7+ / graceful degradation notes
- Guard is server-side (frida-less syscall/API tap on the host), so it works on API 24 targets with no agent in the guest.
- Real Metal fleet spans API 24→35; virtual fleet is listed per-API. If a capability chip is unsupported on the chosen API level, the card greys with "needs API 28+".
- Browser side: WebRTC preferred; fall back to MJPEG-over-HTTP at 15fps for old Chrome/WebView clients. Class strip renders in plain DOM above the canvas, so it survives every fallback path.
- No-WebGL clients: wireframe glyphs are SVG, photo renders lazy-load with a solid-color placeholder.

## Payment notes

## Acceptance criteria
- No screen renders Virtual and Real Metal cards in the same scrolling list.
- Selecting a hardware-bound capability chip hard-disables the Virtual rail with a visible, specific reason string.
- A Camera2/MediaDrm/Telephony/Fingerprint call on a virtual session raises the in-phone migrate sheet within 2s, and one tap re-launches the same APK on Real Metal.
- Class strip is visible in 100% of session frames including the MJPEG fallback; exported reports carry the class and virtual runs are watermarked.
- Checkout preview shows separate per-class line items with distinct rates before confirmation.
