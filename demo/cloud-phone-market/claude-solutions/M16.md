## Mistake restated
GeeLark-style synchronizers broadcast every tap/swipe/keystroke from one "leader" device to N "followers" with a single toggle and no per-action gate. One mis-tap on the leader (wrong button, wrong screen state, an ad interstitial that only appeared on 3 of 40 followers) is replayed everywhere. Result: mass-wrong actions, correlated behavioral fingerprints, and bans. Nobody fixes it because "control 100 phones at once" is the headline feature that sells seats, and cross-device undo is genuinely hard.

## Strlix solution (concrete UX + IA)
Replace "live mirror" with **Rehearse → Preflight → Staged Rollout → Rollback**, driven from inside the phone UI.

1. **Leader is a rehearsal, not a broadcast.** Sync mode records the leader's actions into a *Routine* (ordered steps with target-element semantics captured by the on-device AI: `tap[text="Post"]`, not `tap[540,1820]`). Nothing reaches followers while recording. Bottom sheet shows a live step list you can delete/edit.
2. **Preflight diff (blocking).** Before run, Strlix screenshots each follower and the AI classifies screen state. UI shows three buckets: **Ready (N)** / **Different screen (N)** / **Blocked: login, captcha, update dialog (N)**. Only Ready runs. Tap a bucket → thumbnail grid, tap a thumbnail → live stream of that device.
3. **Canary + staged rollout.** Fixed ladder: 1 device → 10% → rest. Auto-halt after canary if any step's element isn't found or a `risk` screen appears. Between stages: a 15s countdown card with **Hold** button.
4. **Danger-class steps need typed confirmation.** AI tags steps as `read | post | message | follow | purchase | account_settings | delete`. Anything at `purchase`/`account_settings`/`delete` and any step affecting >20 devices requires typing the device count (e.g. `47`) — not a checkbox.
5. **Humanization is mandatory, not optional.** Per-device jitter (400–2500ms), shuffled device order, staggered start window; sync-identical timing is what gets accounts flagged.
6. **Rollback ledger.** Every step logs device, timestamp, pre/post screenshot, and a reverse action when one exists (unfollow, delete post, revert toggle). "Undo run" applies reverses to devices where it's possible and shows an explicit **Cannot undo (N)** list with per-device deep links. Never claim full undo.
7. **Kill switch.** Persistent floating **STOP ALL** during any run; halts queue in <1s and frees all followers.

IA: `Fleet → Routines → [Routine] → Rehearse | Preflight | Run | History`. No global "mirror on" switch anywhere.

## Android 7+ / graceful degradation notes
- Element-semantic targeting needs accessibility tree; if unavailable (API 24 containers, hardened apps), fall back to coordinate replay but **downgrade the run**: canary-only, max 10 devices, banner "Coordinate mode — verify each screen."
- No WebRTC in old WebViews → preflight thumbnails fall back to 2s MJPEG/JPEG polling over the same :8789 endpoint.
- Rollback screenshots capped at 720p JPEG; on low-RAM devices store last 3 steps only.
- `prefers-reduced-motion` / no-JS: preflight page renders as a plain table with a POST form per bucket.

## Payment notes
Not central. If sync scale is a paid tier, gate it with a test-mode Stripe Checkout stub (`sk_test_*`, webhook → `entitlements.sync_max_devices`); unpaid accounts hard-cap at 5 followers. No real charges; `purchase`-class steps inside routines are blocked entirely in test mode.

## Acceptance criteria
- A routine that mis-targets (element absent on followers) halts at the canary and touches ≤1 device.
- Any step affecting >20 devices or tagged `purchase|account_settings|delete` cannot execute without a typed device-count confirmation.
- STOP ALL aborts an in-flight run across 50 devices in under 1 second, verified in the run ledger.
- Every run produces per-device pre/post screenshots and an undo result split into Reverted / Cannot undo.
- Two devices in the same run never execute the same step within 400ms of each other.
